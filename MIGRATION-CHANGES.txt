  Key decisions in this config:
  - strict: true            -> full type safety, no implicit any
  - allowJs: false          -> JavaScript is fully gone; do not allow .js back

                                  (Chrome 111+, Edge 111+, Firefox 111+,
                                   Safari 16.4+)

  Why src/views/ instead of src/pages/ :
    Next.js treats ANY directory named "pages" (at the root OR under src/)
    as the Pages Router. Having src/pages/ next to src/app/ made Next load
    the Pages-Router compatibility type layer, which types usePathname(),
    useParams() and useSearchParams() as possibly-null, and would also have
    tried to build a second Pages-Router tree from those files. Renaming to
    src/views/ removes that conflict entirely.

"use client";

import { useEffect } from "react";
import { useRouter, usePathname } from "next/navigation";
import type { ReactNode } from "react";
import { useAuth } from "@/context/AuthContext";

/**
 * Scrolls the window to the top whenever the route path changes — the
 * App Router equivalent of the old react-router ScrollToTop.
 */
export function ScrollToTop() {
  const pathname = usePathname() ?? "/";

  useEffect(() => {
    window.scrollTo(0, 0);
  }, [pathname]);

  return null;
}

/**
 * Blocks a route behind a logged-in session. While auth is still resolving it
 * renders nothing (no flash of the protected content); once resolution is done
 * and there is no user, it sends the visitor to /login and remembers where
 * they were headed in the `from` query param.
 */
export function ProtectedRoute({ children }: { children: ReactNode }) {
  const { user, ready } = useAuth();
  const router = useRouter();
  const pathname = usePathname() ?? "/";

  useEffect(() => {
    if (ready && !user) {
      router.replace(`/login?from=${encodeURIComponent(pathname)}`);
    }
  }, [ready, user, router, pathname]);

  if (!ready || !user) return null;
  return <>{children}</>;
}

  Behaviour preserved from the original:
    - ScrollToTop: the original used useLocation().pathname as the effect key
      and window.scrollTo(0,0). Identical, with usePathname() instead.
    - ProtectedRoute: the original returned null while !ready, then
      <Navigate to="/login" state={{from}} replace /> when !user. The new
      version returns null in both cases and performs the redirect in an
      effect with router.replace(), so the address bar updates correctly.
    - The `?? "/"` fallbacks on usePathname() are defensive: Next's Pages
      Router compatibility type layer declares usePathname() as
      string | null, even though this app is App-Router-only and never
      actually receives null.

   * Reads and parses JSON from localStorage, falling back to `fallback` when the
   * key is missing or the stored value is not valid JSON. Always call with an
   * explicit fallback so the return type stays honest.
   */
  export function safeParseJSON<T>(key: string, fallback: T): T {
    try {
      const raw = localStorage.getItem(key);
      if (raw === null) return fallback;
      return JSON.parse(raw) as T;
    } catch (e) {
      console.warn(`JSON.parse failed for key "${key}":`, e);
      return fallback;
    }
  }

--------------------------------------------------------------------------------
ISSUE 1: "pages and app directories should not be under the same folder"
--------------------------------------------------------------------------------
  SYMPTOM
    `npm run build` failed immediately with:
      Error: > `pages` and `app` directories should not be under the same
        folder
      at ignore-listed frames

  ROOT CAUSE
    The App Router tree was at the project root (app\) while the page
    components were still in src\pages\. Next.js scans for a directory named
    "pages" at the root AND under src\, so it concluded the project had two
    routers in two different roots.

  FIX
    Moved app\ -> src\app\ so both live under src\. Updated the CSS import
    path inside globals.css from ../src/styles/... to ../styles/....

  VERIFICATION
    Build compiled successfully on the next attempt.

ISSUE 2: ~10 TypeScript errors, "'pathname' is possibly 'null'"
--------------------------------------------------------------------------------
  SYMPTOM
    After the build compiled, `next build`'s TypeScript pass failed with:
      src/components/Navbar.tsx(29,33): error TS18047: 'pathname' is possibly 'null'.
      src/components/RouteUtils.tsx(35,56): error TS2345: Argument of type
        'string | null' is not assignable to parameter of type
        'string | number | boolean'.
      src/views/Category.tsx(75,14): error TS18047: 'params' is possibly 'null'.
      src/views/Checkout.tsx(36,20): error TS18047: 'params' is possibly 'null'.
      src/views/CourseDetails.tsx(34,14): error TS18047: 'params' is possibly 'null'.
      src/views/CoursePlayer.tsx(21,14): error TS18047: 'params' is possibly 'null'.
      src/views/Courses.tsx(45,93) and (47,6): error TS18047: 'searchParams' is possibly 'null'.
      src/views/Login.tsx(17,16): error TS18047: 'searchParams' is possibly 'null'.
      src/views/PaymentSuccess.tsx(21,20): error TS18047: 'pathname' is possibly 'null'.
      src/views/Search.tsx(17,15): error TS18047: 'params' is possibly 'null'.

  ROOT CAUSE
    Next 16's auto-generated next-env.d.ts contains:
      /// <reference types="next/navigation-types/compat/navigation" />
    That compat module augmentation declares:
      usePathname():   string | null
      useParams():     T | null
      useSearchParams(): ReadonlyURLSearchParams | null
    Those nullable types exist for the Pages Router, where the hooks really
    can return null before the router is ready. Because src\pages\ existed
    (see Issue 3), the compat layer was being applied to an App-Router-only
    project.

  FIX
    Handled nullability at every call site rather than editing next-env.d.ts
    (which Next regenerates and forbids hand-editing):
      usePathname()          ->  usePathname() ?? "/"
      useParams<{id}>()      ->  useParams<{id}>() then params?.id ?? ""
      useSearchParams()      ->  useSearchParams()?.get(...) and
                                 searchParams?.toString() ?? ""

    This is defensive but correct regardless of which type layer wins, and
    it costs nothing at runtime in an App Router app where the hooks always
    resolve.

--------------------------------------------------------------------------------
ISSUE 3: src\pages\ was being treated as the Pages Router
--------------------------------------------------------------------------------
  SYMPTOM
    The nullable types from Issue 2 should not have applied at all in a pure
    App Router project — the official Next docs say useParams returns an
    empty object and usePathname returns a string. The mismatch pointed at
    something structural.

  ROOT CAUSE
    The ported page components were placed in src\pages\ (mirroring the old
    folder name). Next.js resolves src\pages as the Pages Router directory.
    Consequences:
      1. The Pages-Router compatibility type layer got loaded (Issue 2).
      2. Next would have tried to build a SECOND router tree from
         src\pages\*.tsx, since every one of those files has a default export
         React component, which is exactly what a Pages Router page is.
         That would have produced duplicate/shadowed routes.

  FIX
    Moved src\pages\ -> src\views\ (15 files) and updated all 16
    src\app\**\page.tsx imports from "@/pages/X" to "@/views/X".

  VERIFICATION
    - tsc --noEmit: exit 0
    - npm run build: all 16 routes listed under "Route (app)", no Pages
      Router routes
    - grep of src\app for "@/pages/": zero matches
    - grep of src for "react-router": only 2 hits, both explanatory comments

--------------------------------------------------------------------------------
ISSUE 4: Next 16 stopped overriding scroll-behavior on navigation
--------------------------------------------------------------------------------
  SYMPTOM
    Not a build error — a silent behaviour regression that would only show up
    in the browser.

  ROOT CAUSE
    From the official Next 16 upgrade guide, section "Scroll Behavior Override":
      "In Next.js 16, this behavior has changed. By default, Next.js will no
       longer override your scroll-behavior setting during navigation."
    The project CSS sets html { scroll-behavior: smooth; }, and the app has a
    ScrollToTop component that calls window.scrollTo(0, 0) on every pathname
    change. In Next 15 and earlier, Next temporarily forced scroll-behavior to
    auto during navigation so that scroll-to-top was instant. In Next 16, that
    override is gone by default, so every route change would have ANIMATED
    from the bottom of the old page to the top of the new one — exactly the
    jank the original override existed to prevent.

  FIX
    Per the Next 16 docs, opted back in by adding the data attribute to the
    root <html> element in src\app\layout.tsx:
      <html lang="en" className="..." data-scroll-behavior="smooth">

    This restores the previous default: Next temporarily sets
    scroll-behavior to auto during the transition, performs the navigation
    (instant scroll to top), then restores the smooth value for in-page
    scrolling.

19. BEHAVIORAL DECISIONS AND TRADE-OFFS
================================================================================

  DECISION 1: Client component architecture preserved.
    The entire app is client-rendered, backed by localStorage for auth,
    enrollments and streaks. No Server Components, no Server Actions, no
    data fetching. This was a deliberate fidelity choice — the brief was to
    migrate the framework and language, not to re-architect the data layer.
    "use client" appears in 28 files. Every route wrapper in src\app\ is a
    server component that renders one, which keeps the door open for moving
    individual pages to the server later without touching the route files.

  DECISION 2: next/font instead of Google Fonts @import.
    next/font is the idiomatic Next.js approach: it downloads the font files
    at build time, self-hosts them, and eliminates the runtime request to
    fonts.googleapis.com (which was a render-blocking network fetch in the
    Vite app). Outfit and Space Grotesk are both on Google Fonts and were
    loaded successfully. Cabinet Grotesk is NOT on Google Fonts (it is a
    Fontshare family) — the original CSS requested it from Google, which
    would have 400'd and silently fallen back. The new stack keeps
    "Cabinet Grotesk" first so locally-installed copies still win, and
    self-hosts the two real fallbacks.

  DECISION 3: src\views\ instead of src\pages\.
    See Issue 3. This is a hard requirement, not a style preference.

  DECISION 4: Suspense wrappers on all 16 routes.
    Six pages call useSearchParams/usePathname (Courses, Search, Login,
    Navbar inside the layout, PaymentSuccess, RouteUtils inside protected
    routes). Next requires useSearchParams to sit under a Suspense boundary
    for static prerendering, or the build fails with "useSearchParams()
    should be wrapped in a suspense boundary". Rather than sprinkle
    Suspense inconsistently, every route wrapper got one. The cost is 9-12
    lines per route file; the benefit is a uniform, future-proof pattern and
    a guaranteed-correct build.

  DECISION 5: qs `?from=` instead of router state for the login redirect.
    react-router's location.state is in-memory and does not survive a page
    refresh. A query parameter does, and it is the documented App Router
    pattern. The guard is `from.startsWith("/")` before the redirect is
    followed, so a crafted ?from=https://evil.example link cannot be used
    for an open redirect.

  DECISION 6: keep the two src\styles\ CSS files, keep the 12 stubs.
    awwwards.css (71 lines) and components.css (125 lines) contain real,
    actively-used CSS (.btn variants, .aw-hero-h1, .aw-grain,
    .aw-marquee-track, .carousel-dot, .aw-stack-card) and are imported by
    globals.css. The other 12 files are single-line comment stubs left over
    from the original project. They were retained rather than deleted because
    removing files outside the migration's stated scope was not requested.

  DECISION 7: preserve two original behaviour quirks.
    See section 17m. Both are two-line fixes in EnrollmentContext.tsx if they
    are ever wanted.

  DECISION 8: playwright-core left in devDependencies.
    It was present in the original package.json and is not referenced anywhere
    in src\ or in any script. Removing it was not part of the request, so it
    was left alone. It is inert.

  DECISION 9: Tailwind v4 kept, integrated via PostCSS.
    The brief specified "Keep Tailwind v4". Tailwind v4 has no
    tailwind.config.js — configuration lives in CSS via @theme, which is how
    the original project already worked. The only change was swapping
    @tailwindcss/vite for @tailwindcss/postcss and adding
    postcss.config.mjs.

  DECISION 10: no new dependencies beyond what the migration requires.
    Nothing was added for data fetching, state management, forms, tables,
    toasts, icons, or animation beyond what the original project already used.
    framer-motion, gsap, @gsap/react and @phosphor-icons/react are unchanged.

21. CAVEATS — WHAT NOT TO BREAK
================================================================================

  CAVEAT 1 — Do NOT change tsconfig.json "jsx" back to "preserve".
    Next.js auto-rewrote it to "react-jsx" (the React automatic runtime) and
    that value is mandatory. Changing it back will fail the build.

  CAVEAT 2 — Do NOT rename src\views back to src\pages.
    Any directory named "pages" (at the root or under src/) is interpreted by
    Next as the Pages Router. That reintroduces the nullable compat types and
    would attempt to build a second router tree.

  CAVEAT 3 — Do NOT edit next-env.d.ts by hand.
    Next.js regenerates it. It contains the reference to
    next/navigation-types/compat/navigation, which is why usePathname() and
    friends are typed as possibly-null.

  CAVEAT 4 — Do NOT add an "eslint" key to next.config.ts.
    Next 16 removed the eslint config option and the `next lint` command.
    Linting is `npm run lint` (oxlint).

  CAVEAT 5 — Do NOT add a custom webpack config to next.config.ts.
    Next 16 uses Turbopack by default for both `next dev` and `next build`.
    If a webpack option is present, the build FAILS. If a plugin is found to
    be injecting one, use `next build --webpack` to opt out, or migrate the
    config to the equivalent `turbopack.*` option.

  CAVEAT 6 — Keep the `?? "/"` / `?.id ?? ""` / `?.get()` guards on the
    navigation hooks, or the project will stop compiling.
    They are required by the Pages-Router compat type layer that next-env.d.ts
    always loads.

  CAVEAT 7 — Keep postcss.config.mjs.
    Without it, Tailwind v4 utilities silently stop being generated and the
    entire UI renders unstyled while the build still "succeeds".

  CAVEAT 8 — Keep data-scroll-behavior="smooth" on the <html> element.
    Removing it reintroduces the animated scroll-to-top on every navigation
    (Issue 4).

  CAVEAT 9 — GSAP must always be imported via @/utils/gsap.
    Importing gsap or gsap/ScrollTrigger directly in a component means
    registerPlugin is no longer guarded by the typeof window check and will
    run during SSR.

  CAVEAT 10 — verbatimModuleSyntax is on.
    Type-only imports must use `import type { ... }`. Plain value imports of
    types will fail to compile.

  CAVEAT 11 — allowJs is false.
    If any .js file is ever reintroduced into src\, TypeScript will refuse to
    compile it. That is intentional — the project is fully TypeScript.

  CAVEAT 12 — Protected routes render null until auth resolves.
    This is by design (it prevents a flash of protected content) and matches
    the original app. If you want a loading state instead, wrap the children
    in PageLoader inside ProtectedRoute rather than removing the null return.
